## Proposed 90-minute budget

This is a delivery budget, not a measured full-length rehearsal. Automated tests exercise behavior, not speaking and moderation time.

| Minutes | Segment                                                                      | Evidence to preserve                                                      |
| ------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 0–10    | Opening: join, practice, app context, audience needs/theme and first build   | First build starts before Past                                            |
| 10–35   | Past: historical visions, CERN, browser foundations, editors and native form | Inspect the document after Dreamweaver; trace POST → Database → GET       |
| 35–55   | Present: priority, build, AJAX and browser applications                      | Client-side interaction state and shared results                          |
| 55–75   | Future: lecturer outlook, priority, contract, build and comparison           | Same task and source revision in fixed/generated views; inspect one claim |
| 75–80   | Recap, possible directions and SDLCAI invitation                             | Main messages and a concrete next opportunity                             |
| 80–90   | Reserved recovery and questions                                              | Do not pre-fill this margin with more exposition                          |

Four explicit builds run during explanation, not as four separate waiting periods. At each checkpoint, use the observed app if ready; otherwise use a clearly identified prepared baseline or state that the result is unavailable. A completed model turn is not a passed acceptance test.

## Launches and checkpoints

1. **build-document** starts in Opening, immediately after the practice activities, seminar-app introduction, audience-needs cloud and theme vote. Approve the needs, freeze the theme and explicitly start the build before entering Past. Discuss the historical visions, CERN, browser foundations and editors while it runs. Keep **check-document** after Dreamweaver and revisit the approved needs there.
2. **build-forms** follows the proposed survey fields. Trace the native flow while it runs. Submit only at **check-native-form**.
3. **build-application** follows Present needs and the interaction-priority vote. The vote selects the FIRST acceptance test: confirmation, preservation, or shared updates. Keep all baseline protections. Show expected → observed → result at the checkpoint.
4. **build-agents** follows the lecturer outlook, focused seminar-priority vote and runtime contract. Compare fixed and generated views on the same task and frozen source revision. Verify one claim and one permitted action.

Navigation opens audience activities but never starts implementation. **Start this build** launches the reviewed prompt. **Retry this build** reuses the failed attempt’s original approved inputs.
