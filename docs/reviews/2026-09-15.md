# Strict lecture and infrastructure review

Reviewed 15 September 2026 against commit `443cb8f`, with 94 exported slides. Target: early MSc students; documented duration: 90 minutes plus up to 15 minutes of slack.

## Assessment

The lecture has a defensible central argument: organizing information, enabling interaction, and delegating tasks all require explicit structure and evidence. Its current infrastructure is **not yet reliable enough for a lecture without prepared recovery paths**. Several recent word-cloud and navigation additions bypass assumptions enforced elsewhere.

The existing quality gate passes: **53 unit/integration tests and 27 browser tests**, plus formatting, types, lint, architecture, dependency audits and Worker build. Additional isolated probes nevertheless reproduced the failures below. Passing the existing suite does not establish readiness of the actual lecture sequence.

This was a review, not an implementation pass. No maintained source or lecture content was changed. Test votes and responses went only to disposable local Workers. No production votes, collections, builds, or deployments were changed.

**Priority:** P1 = fix before relying on the live lecture. P2 = significant reliability, security, or teaching improvement. Findings marked “reproduced” were exercised; others follow from the cited code or are explicitly teaching judgments.

## P1 — live-session blockers and data loss

### 1. The Present priority poll does not exist in the Worker — reproduced

Slide 39, `vote-interaction`, names `webdev-2026-interaction`. The Worker defines only friction, theme and priority rooms. The actual local Worker returned **404** for the interaction room. Opening this slide cannot open voting, and the Present build depends on its decision. The existing tests iterate over the three Worker rooms, so they cannot detect the omitted fourth deck room.

Evidence: [deck: room and choices](../../docs/presentations/web-development-2026.md:498), [Worker room definitions](../../audience/worker.ts:10).

**Change:** Define and initialize the interaction room, and validate every poll in the real deck against the Worker configuration before presenting. Share a definition or generate a manifest rather than maintaining two independent lists.

### 2. Starting or resuming Live on a word-cloud slide fails — reproduced

Live-on calls `syncWordCloud(true)` before setting `live = true` or delivering the live stage. The Worker refuses to start a collection unless its stored stage is already live. With a waiting stage, the result is **400: Turn Live on first**. Starting on a normal title works. Live-off followed by Live-on while selecting a word-cloud slide reproduces the same error.

Evidence: [Live-on ordering](../../server.ts:553), [Worker collection prerequisite](../../audience/stage-state.ts:58).

**Change:** Make broadcast activation and collection activation an ordered transition with explicit rollback/error handling. Test cold startup, resume, and slow/failing publication against the real Worker, not a mock that accepts every feedback request.

### 3. An old poll can still replace a later question in Live — reproduced

Leaving a poll for a non-poll slide does not close it. Ordinary discussion questions also publish `projectionKind: "question"`. The Worker interprets that as permission to show the first open poll, without matching it to the projected slide.

Reproduction: show the friction poll, then show “Which ambition does your everyday software serve?” Stage contains the discussion question, while the audience response contains `poll.id = webdev-2026-friction`; the browser gives that poll precedence.

Evidence: [poll transition early return](../../server.ts:155), [audience poll selection](../../audience/worker.ts:203), [browser poll precedence](../../audience/audience.ts:102).

**Change:** Publish a specific poll ID and a distinct poll projection type. Show a poll only when that ID matches. Define and test whether leaving any poll closes it; do not infer poll identity from the general word “question.”

### 4. Returning to a word-cloud slide silently replaces its responses — reproduced

After leaving a cloud, `wordCloudStep` becomes null. Returning calls `action: "start"`, which deletes the Worker’s feedback rows and creates a new round. In the probe, an approved `date` response appeared in the review; returning to the collection changed its round and left **zero items**. Subsequent capture can overwrite that slide’s saved findings with an empty list.

The manual “Open new collection” control asks before removing responses, but automatic navigation bypasses that protection. A newly started different collection also replaces any unresolved questions in the shared feedback queue.

Evidence: [automatic collection lifecycle](../../server.ts:187), [replacement storage](../../audience/stage-state.ts:70), [manual confirmation](../../public/feedback.ts:62).

**Change:** Give each lecture and slide a persistent collection identity. Revisit/resume the existing round; reset only at explicit new-lecture/new-collection boundaries. Preserve approved findings separately from an editable queue, and keep audience questions separate from slide word clouds.

### 5. The default builder workspace is the controller repository — verified configuration defect

The default `../lecture-studio`, resolved from this repository, resolves back to this repository itself. The supplied `.env.example` repeats it. The Codex bridge rejects the filesystem root and home directory, but accepts the controller checkout. A fresh installation without a saved rehearsal can therefore authorize the implementation agent to modify the studio, instead of an isolated seminar app.

Evidence: [startup default](../../server.ts:1044), [workspace validation](../../lib/codex.ts:162), [example configuration](../../.env.example:3).

**Change:** Require a verified separate rehearsal checkout, or create one before enabling builds. Reject the controller root and validate the expected starter contract. Explicitly configured and saved rehearsal paths may avoid this defect; it is the default path that is unsafe.

### 6. A failed or interrupted build cannot be retried normally — reproduced

Starting a build permanently adds its slide to `presentation.runs`. Both the API and desk disable starting that slide again solely because a run exists; they do not distinguish completed, failed, or interrupted runs. An isolated mock-agent probe returned 200 for the first launch, then 400, “This step has already started in this session,” after the agent was ready again with a failed outcome. An asynchronously failed generation therefore requires restarting the presentation or working around its controls, risking loss of collected decisions. The guard correctly prevents duplicate concurrent launches, but also prevents recovery.

Evidence: [API guard and run recording](../../server.ts:689), [desk disable condition](../../public/presentation.ts:465).

**Change:** Track each run’s lifecycle and allow an explicit retry after failure/interruption while preserving approved inputs. Pair this with a prepared app snapshot for each checkpoint. A preview URL is not evidence of a successful build.

## P2 — privacy, integrity, and operational reliability

### 7. “Send privately” does not explain that approved words enter model prompts

The student form says responses are private unless selected for discussion. Approval later places words in `approvedWords`; the first, Present and Future prompts can send those words to the remote implementation model. The README also says submitted material is not automatically sent to Codex. There is no explanation at submission that moderator approval can make a response part of a build prompt.

This is a disclosure and operator-understanding problem, not a claim that all raw submissions are being sent: pending words are filtered out, and build launch is explicit.

Evidence: [student notice](../../audience/audience.ts:24), [capture](../../server.ts:178), [prompt inclusion](../../lib/presentation.ts:206), [README promise](../../README.md:7).

**Change:** Explain possible projection and model use before submission, and make the lecturer’s approval scope clear. Keep unapproved input private. Explain retention for model conversations and generated artifacts separately from the Worker queue’s 24-hour expiry.

### 8. Poll totals are easily inflated — reproduced, with bounded local requests

The vote endpoint creates a new voter identity whenever no valid cookie is supplied. It has no comparable per-network/collection admission limit to feedback. Eight local POSTs without retained cookies produced **eight additional votes** from one script. An Origin check protects browser cross-origin requests; it does not authenticate a non-browser caller.

Evidence: [identity creation and voting](../../audience/room-http.ts:52), [unbounded vote insertion](../../audience/room-state.ts:67).

**Change:** Treat counts explicitly as informal participation signals, and add classroom-appropriate rate/admission controls. If trustworthy one-person voting is required, anonymous cookies alone cannot provide it. Do not introduce a restrictive per-IP limit that prevents a classroom behind one network from participating.

### 9. Supported word-cloud sizes can make a slide impossible to display — reproduced

Each collection accepts up to 500 items. The cloud display groups terms and caps its output, but review slides and build prompts append every approved item without deduplication or a total limit. The closing slide aggregates four collections. A valid-size input set produced a **48,071-character body**, rejected by `validateDraft` as `Invalid stage body`; navigation fails instead of displaying a recap. Far fewer items already overwhelm a projected slide.

Evidence: [unbounded review expansion](../../lib/presentation.ts:218), [bounded cloud rendering for contrast](../../lib/feedback.ts:80), [closing dependencies](../../docs/presentations/web-development-2026.md:1084), [body validation](../../lib/material.ts:151).

**Change:** Aggregate duplicate terms with counts, select a small number of findings for projection, and budget prompt length before display or build launch. Keep the complete reviewed set privately available. Validate `wordsFrom` and `reviewWordsFrom` references as strictly as poll and preview references; currently mistyped references silently look like missing audience input.

### 10. Local/Worker compatibility is discovered at the moment of presenting

The recent Live-toggle outage was caused by running the new local reset client before its Worker deployment completed. The local UI reports a generic reset/deploy error only after Live-on is attempted. CI’s deployed smoke check asks only whether `/api/audience` succeeds; it does not advertise or verify the protocol required by the local studio.

Evidence: [startup dependency](../../server.ts:527), [deployment smoke check](../../.github/workflows/deploy-audience.yml:39).

**Change:** Add a read-only capability/version endpoint and a clear readiness indicator. Check required rooms and protocol compatibility when loading the lecture, not after audience activation. Prefer backward-compatible rollout order for changes affecting startup.

### 11. The test suite does not cover the actual lecture as a system

The full gate passes despite findings 1–4. The build workflow uses a tiny synthetic theme-poll deck; the broadcast fixture accepts feedback without enforcing the real Worker’s Live prerequisite. Layout tests exercise selected fixtures and diagrams rather than populated review slides. These tests are useful but do not cover the interactions now depended on during teaching.

Evidence: [synthetic build workflow](../../browser-tests/build-workflow.spec.ts:10), [feedback mock](../../tests/audience-broadcast.test.ts:18), [layout fixture](../../browser-tests/slide-layout.spec.ts:1).

**Change:** Add one real-deck rehearsal against a disposable real Worker: cold start, each poll/word-cloud entry, close/revisit/resume, build-input capture, failed-build retry, and checkpoints with realistic response counts. Keep focused unit tests; supplement them with this system test.

## Presentation logic and pedagogy — judgments for early MSc students

### 12. Make assessable learning outcomes explicit

The opening and TOC state topics and a broad question, but do not say what students should be able to explain or decide afterwards. Word clouds and theme votes gather useful design input; they do not establish understanding of request lifecycles, failure states, or agent constraints.

Evidence: [opening and TOC](../../docs/presentations/web-development-2026.md:15), [closing activity](../../docs/presentations/web-development-2026.md:1065).

**Change:** Use three observable outcomes, then assess each briefly:

1. Trace a form submission from browser to storage to rendered result; explain what AJAX changes and what it does not.
2. Choose a working baseline and explain what the user can know when a request or response fails.
3. Evaluate a generated view using source evidence, permitted actions and an explicit success criterion.

Keep the historical examples as explanations for these design choices. End with a short transfer problem using another application, not only another preference cloud. This recommendation follows the alignment of objectives, practice and assessment described by [CMU’s Eberly Center](https://www.cmu.edu/teaching/assessment/basics/alignment.html); it is not a measured evaluation of this class.

### 13. Separate the two network-failure experiments

Slide 57 disconnects the browser _before_ submission. Slide 58 shows a write that succeeds but whose response is lost. The first experiment does not establish the second scenario. The speaker notes make this distinction, but the visible activity and mechanism should make it unavoidable for students.

Evidence: [activity and next diagram](../../docs/presentations/web-development-2026.md:735).

**Change:** Show two controlled cases: request never reaches the server; server stores the response and the response is deliberately dropped. Ask students to predict browser knowledge and server state separately, then inspect the evidence. Prepare this failure injection in advance rather than attempting to time a network disconnection live.

### 14. Several tasks ask students to inspect an app before it is on screen

Slide 28 tells students to submit the new seminar-interest response before its build at slide 30. Slide 55 says “Submit here” but has no `previewOf`, so it renders instructional text rather than the app; the automatic interactive checkpoint is at slide 59. Slide 79 asks students to inspect generated output before the automatic preview at slide 80. The presenter can work around these through manual preview controls, but the visible sequence is not self-sufficient.

Evidence: [form introduction](../../docs/presentations/web-development-2026.md:365), [submit-here slide](../../docs/presentations/web-development-2026.md:715), [output inspection](../../docs/presentations/web-development-2026.md:1016), [preview behavior](../../server.ts:211).

**Change:** Introduce future fields in future tense, then ask for submissions at the actual app checkpoint. Embed or open the app before the evidence task, with a clear return to discussion. Make the displayed endpoint and flow diagram match the implementation: the native prompt currently describes a confirmation with submitted values, while the diagram specifically fetches an aggregate at `/results`.

### 15. The conceptual step from HTML to generated interfaces needs more scaffolding

The deck moves from a small HTML example to SSR/CSR, regeneration, shared state, behavioral affordances, and a “composition contract.” Several terms are carried mainly by speaker notes. The Future build uses the contract before the slides explain its inputs and receipt. A generated seminar view illustrates constrained presentation; it is not itself evidence that an agent can safely discover and execute arbitrary service actions.

Evidence: [rendering slides](../../docs/presentations/web-development-2026.md:578), [Future build](../../docs/presentations/web-development-2026.md:849), [action claim](../../docs/presentations/web-development-2026.md:964).

**Change:** Add a compact architecture map distinguishing lecture controls, demo app, implementation agent, and runtime composition model. Put the runtime contract before the Future build: inputs, permitted output/actions, validation and fallback. Compare a fixed and generated view on the same task. State which broader agent claims are hypotheses, and what evidence would challenge them. Keep the existing explicit hypothesis labels.

### 16. Rebalance pacing and make audience influence observable

There are 85 slides before References, including four builds, four polls, five word clouds and several pair discussions. Twelve of those slides stage three flows, so raw slide count alone is not proof of overload. Nevertheless, moderation, build checks and discussion consume time that the older 90-minute run-of-show has not been rebudgeted to reflect. Related stretches repeat the same idea: links on slides 18–19, agent-interface directions on 67–68, and explicit actions on 74–76.

The Present vote also asks students to prioritize preserving unsent input or updating shared results, while the base build already requires both. “Priority” may change emphasis, but its observable effect is underspecified.

Evidence: [documented duration](../../LECTURE-NARRATIVE.md:16), [Present choices and prompt](../../docs/presentations/web-development-2026.md:498).

**Change:** Rehearse with a timed 90-minute budget, reserve an explicit recovery margin, and identify slides that can be skipped. Keep the native/AJAX comparison and reduce repeated expository diagrams. Let a vote choose a measurable enhancement, the first test to run, or a real design tradeoff; make the consequence visible at the checkpoint. Word clouds should gather needs, while prediction and explanation tasks check learning. Evidence for active learning in STEM supports meaningful student work, not the assumption that any polling widget improves learning: [Freeman et al., 2014](https://doi.org/10.1073/pnas.1319030111).

### 17. Protect the historical content and operator instructions from drift

Six historical slides are effectively image-only. Their central arguments depend on narration and remotely loaded images; the deck does not package a fallback copy. Notes and documentation also retain obsolete instructions: manually reopening automatic word collections, manually closing votes before Live-off, and an older slide order. The Future section cites an unpublished position paper without a student-accessible copy or excerpt.

Evidence: [Bush slide](../../docs/presentations/web-development-2026.md:201), [obsolete closing-cloud instructions](../../docs/presentations/web-development-2026.md:1070), [README Live instructions](../../README.md:39), [unpublished source](../../docs/presentations/web-development-2026.md:1123).

**Change:** Cache permitted image assets with attribution; put one short interpretive claim beside each crucial historical image. Update one canonical operator guide from the current workflow. Provide students with an accessible hypothesis summary or shareable manuscript excerpt. The sampled CERN and early-OWA source claims checked out against [Berners-Lee’s proposal](https://www.w3.org/History/1989/proposal.html) and [Hopmann’s firsthand account](https://www.alexhopmann.com/page/the-story-of-xmlhttp); this was not a complete audit of every reference or image permission.

## What is already sound

- Loopback binding, exact Host/Origin checks, separate desk/stage capability tokens and same-origin writes are appropriate protections for a local single-presenter studio.
- Presenter endpoints use a secret and timing-safe comparison; SQL writes use bound parameters. I did not reproduce an unauthenticated presenter takeover or a student-to-script-injection path.
- Markdown escapes raw HTML; feedback text is normalized, bounded and moderated before cloud projection. Public audience state is explicitly allowlisted.
- The builder disables configured connectors/plugins and removes lecture/Obsidian environment variables. This is useful context reduction, although it is not a complete secret or filesystem isolation boundary.
- Native form submission, preserved unsent input, source checking and fallback behavior are good learning targets.
- The historical and Future material generally distinguishes teaching diagrams, historical artifacts and hypotheses. Preserve that discipline.

## Recommended order

1. Fix findings 1–6 and add a real-deck/real-Worker rehearsal covering them.
2. Fix response disclosure, output limits and compatibility readiness; decide the required strength of vote integrity.
3. Reorder the concrete demos and failure experiment, state three learning outcomes, and make the final task test transfer.
4. Rehearse the complete delivery with a recovery margin and prepared app snapshots. Update the run-of-show and cached teaching assets after that rehearsal.
